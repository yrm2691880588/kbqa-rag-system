# KBQA-RAG · 电商知识库问答系统

一个从 0 到 1 独立搭建的 **RAG（检索增强生成）智能问答系统**：把商品说明书、价格表、营销文档等资料传进知识库，AI 就能基于这些资料准确回答用户问题，并像打字机一样实时输出回答。

> 面向「知识库问答」场景的完整落地实践，覆盖 账号体系 → 文档解析 → 向量检索 → AI 生成回答 的完整链路。

## 🏗️ 系统架构

```
┌─────────────────────────────────────────────────────────┐
│  前端 Vue3 (Vite)           http://127.0.0.1:5173*      │
│  登录 / 知识库 / 聊天界面                                 │
└──────────────────────┬──────────────────────────────────┘
                       │ REST + SSE(流式)
┌──────────────────────▼──────────────────────────────────┐
│  后端 FastAPI           http://127.0.0.1:8000  /docs *  │
│                                                         │
│  ① 文档入库链路:  解析 → 切块 → 向量化 → 写入 Qdrant      │
│  ② 问答链路:      问题 → 向量检索 → 文档去噪 → 生成回答    │
│  ③ 体验模块:      闲聊识别 / 开放意图识别 / 会话记忆        │
└───────┬───────────────────────────┬─────────────────────┘
        │                           │
┌───────▼─────────┐      ┌──────────▼──────────┐
│  PostgreSQL 16  │      │  Qdrant 向量库       │
│  业务数据        │      │  文档向量 + 检索      │
└─────────────────┘      └─────────────────────┘
```

> \* 端口可在项目根目录 `.env` 的 `FRONTEND_PORT` / `BACKEND_PORT` 修改。
> 开发机上 8000/5173 常被其他项目占用，撞车时启动脚本会提示并给出改法。

**问答核心流程（RAG）**

1. 用户提问 → 后端先做**意图判断**（寒暄？开放列举？还是真问题？）
2. 真问题 → 问题文本转成向量 → 到 Qdrant 里取回最相似的候选片段
3. **文档级去噪**：候选片段先按"文档"归类，剔除明显低于同文档最佳命中的噪声片段
4. 命中片段 + 系统提示词 拼给 DeepSeek → 生成带依据的回答，SSE 流式返回
5. 没命中 → 明确回答"知识库中没有相关信息"，不乱编

## 🧩 多领域与项目导出

本项目支持**多个业务领域**（电商、财经、通用），领域内容集中在 `backend/app/domain/`。
通用的 RAG 引擎、多租户隔离、额度控制等属于 Core，与领域无关。

### 在母项目中切换领域

```bash
DOMAIN=ecommerce   # 电商
DOMAIN=finance     # 财经
DOMAIN=generic     # 通用（默认）
```

> 生产环境（`APP_ENV=prod`）必须显式指定领域，不允许用 `generic` 兜底 ——
> 兜底领域的提示词刻意保持中性，上线后忘记配置会静默降低回答质量。

### 导出某个领域为独立项目

```bash
python scripts/extract.py ecommerce ../kbqa-ecommerce
python scripts/extract.py finance   ../kbqa-finance
```

产物是一个**完整、可独立运行**的项目：只含 Core + 该领域，
拍平为标准目录结构，多领域机制已移除，并带自己的 README 与样例资料。

### ⚠️ 导出即分叉

**导出后的项目与母项目不再关联。** 母项目 `core` 的后续更新（修 bug、加功能）
**不会**自动同步到已导出的项目。

这是刻意的设计：导出项目是给使用者二次开发用的，
如果自动同步会覆盖他们自己的改动。相关决策见
[docs/adr/0002](../docs/adr/0002-export-forks-no-core-sync.md)（仅本地保留）。

如果你在母项目里修了通用引擎的重要问题，需要手动合并到各导出项目，
或重新导出后对照修改。每个产物根目录的 `.exported-from` 记录了来源与导出时间。

## 🧠 智能问答能力

除了基础的「检索 + 生成」，系统还实现了四层增强。这些能力**按领域配置启用**，
用不上的领域不会产生额外开销。

### 1. 多轮问题改写

用户在追问里常说「这三家」「它们」，而知识库文档里写的是具体名称 ——
直接拿指代词去检索必然搜不到。

系统在检索前先把问题改写成自包含的查询：

```
历史：问过「A、B、C 三家公司」
当前：这三家谁的利润最好？
  ↓ 改写
检索用：A B C 利润 对比
```

配置项：`query_rewrite_enabled`，关闭后行为与不加此功能一致。

### 2. 答案自检与打回重做

生成答案后再检查一遍：关键事实能否在资料里找到？有没有编造？是否答非所问？

不合格就把「哪里不对」告诉模型重做，最多重试 `answer_verify_rounds` 次
（财经领域配 2 次，通用领域配 0 次即关闭）。

**用完次数仍不合格时会明确告知「无法给出可靠回答」，绝不硬编。**

### 3. 意图分流

不同问题走不同路径，避免「全都去检索」造成的浪费和危险回答：

| 问题类型 | 处理方式 |
|---|---|
| 闲聊（你好/你是谁） | 直接回应，不查库 |
| 违规（预测股价/推荐股票） | 按领域禁令拒答 |
| 需要实时数据（天气/股价） | 告知无法获取 + 给出知识库能帮什么 |
| 明显无关（菜谱/娱乐） | 超出范围，明确告知 |
| 正常业务问题 | 走知识库检索 |

### 4. 工具调用

模型可以调用工具获得比「心算」可靠的结果：

| 工具 | 用途 |
|---|---|
| `calculator` | 算术计算（增长率、占比、差额、单位换算） |
| `date_range` | 相对时间解析（「去年Q3」→ 2025-07-01 ~ 09-30） |

**为什么需要**：模型对「去年 Q3」的年份换算经常出错，财务数据差一年就全错；
而算术心算也不可靠。工具让这些计算变成确定性操作。

**按领域启用**：`domain.allowed_tools`，默认空（不启用）。
财经领域全开，通用领域不开。

约束：
- 单次问答最多 3 轮工具调用（防死循环烧钱）
- 计算器用字符白名单 + 自写解析器，**不用 eval**（防注入）

### 领域数据隔离

切换领域后，知识库、会话历史、检索结果都按领域隔离 ——
在财经领域看不到电商领域建的库和会话。

实现方式：`knowledge_bases` / `sessions` 表带 `domain` 字段，
列表查询、检索链、按 id 取单个库都做校验。

### 界面显示当前领域

侧边栏显示「知识库问答 [财经]」，浏览器标签显示「财经 · 知识库问答」，
随时能看出当前加载的是哪个领域。

## 📐 质量评估

改检索参数、分块策略、提示词之后，怎么知道到底变好了还是变差了？

项目自带一套**双层评估**，用一组真实问题跑出可对比的数字：

```bash
cd backend
python scripts/eval_all.py --set eval/eval_set.finance.json --kb 财经示例库
```

输出两层指标：

| 层 | 测什么 | 指标 |
|---|---|---|
| 检索层 | 有没有找对文档 | Hit@1 / Hit@3 / MRR |
| 回答层 | 回答里有没有正确答案 | 关键词命中率 |

**两层都要看。** 只测检索层会漏掉「检索对了但模型说没有」的情况 ——
这个坑本项目真实踩过：检索把正确片段送进提示词了，模型仍然答"资料里没有"。

加 `--skip-answer` 可只跑检索层（快，不花钱）；加 `--json 报告.json`
把结果存下来，下次改完再跑一遍就能对比。

## 🧮 表格精确查询（可选工具）

向量检索擅长"意思相近"，但有件事它做不到：

- 「某公司前三个季度的收入**合计**是多少」→ 需要把几个数字**相加**
- 「哪个对象的人数最多」→ 答案是纯数字，全文索引匹配不到

这类问题需要**结构化查询**，所以项目内置了一个工具：
当问题涉及精确数字、聚合、条件筛选时，模型会去查原始 Excel。

工具只做四件事（刻意做窄，避免模型用错）：

```
list_tables   列出有哪些工作表
describe      查看某张表的列名
query         按条件筛选行
sum           对某列求和（返回明细便于核对）
```

**关键设计**：列名写错时**直接报错**并列出可用列名，而不是静默忽略条件。
后者会导致"过滤条件失效、把整张表加起来"，给出一个看似合理的错数 ——
这比报错危险得多。

这个工具默认只在财经领域启用（`allowed_tools` 里配置）。其他领域想用，
在对应领域的配置里加上 `table_query` 即可。

## 🔀 重排模型（可选，默认不启用）

检索出来的候选片段可以再交给重排模型精挑一遍，能明显提升准确率：

| | 有重排 | 无重排 |
|---|---|---|
| 检索命中率（前 3 条） | 96% | 80% |
| 回答准确率 | 100% | 76% |

### 为什么是"可选"

重排**不是**项目依赖。你可能：

- 用云 API 做重排（配 `RERANK_API_KEY` + `RERANK_MODEL`）
- 用本地模型（配 `RERANK_LOCAL_URL` 指向自己的服务）
- 完全不用（什么都不配，自动降级）

**项目只管「怎么调用」，不管「怎么启动」。** 重排服务的启停完全由你决定 ——
可以是命令行、系统服务、Docker，甚至部署在另一台机器上。

### 想用本地模型？

`backend/scripts/rerank_server.py` 是一个参考实现，实现两个接口：

```
POST /rerank   {"query": "...", "documents": ["片段1", "片段2"]}
            →  {"scores": [0.92, 0.35]}

GET  /health   →  {"ok": true}
```

`scores` 与 `documents` 一一对应，数值越大越相关。
你可以直接用它，也可以用任何实现了这个接口的服务。启动方式：

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install sentence-transformers fastapi uvicorn

python scripts/rerank_server.py --port 8020 --model BAAI/bge-reranker-base
```

然后在 `backend/.env` 里配置：

```ini
RERANK_LOCAL_URL=http://127.0.0.1:8020
```

**不要把它塞进主后端的启动脚本。** 它是独立服务，`停止.bat` 也不会管它 ——
这是刻意的设计，避免项目去管理一个它不该管理的东西。

## 🚀 快速启动

### ⭐ 最省事：双击两个脚本（推荐）

项目根目录有两个一键脚本，**不用记命令、不用找脚本在哪**：

| 脚本 | 作用 |
|---|---|
| **[选择启动.bat](选择启动.bat)** | 方向键选领域 → 自动完成：检查环境 → 起数据库容器并等健康 → 起后端并等就绪 → 起前端 |
| **[停止.bat](停止.bat)** | 一键停掉前后端进程 + 数据库容器（**数据保留**，下次启动还在） |

**第一次使用**，仍需先做两步准备：

1. 配置密钥：把 `backend/.env.example` 复制成 `backend/.env`，
   填入你自己的 `EMBEDDING_API_KEY`（阿里云百炼）与 `LLM_API_KEY`（DeepSeek）
2. 装依赖：`cd frontend` 然后 `npm install`

之后每天只要**双击「选择启动.bat」**即可（方向键选领域，回车启动）。

### 端口被别的项目占用？

开发机上常常同时跑着好几个项目，`8000`/`5173`/`5432` 这几个端口最容易撞车。
本项目**不会去抢别人的端口**，端口都可以在项目根目录的 `.env` 里改：

```ini
# 数据库在宿主机上的端口（默认 5432，撞车就改）
POSTGRES_HOST_PORT=5433
# 后端端口（默认 8000）
BACKEND_PORT=8010
# 前端端口（默认 5173）
FRONTEND_PORT=5180
```

改完之后：

| 改的是 | 还要同步改哪里 |
|---|---|
| `POSTGRES_HOST_PORT` | `backend/.env` 里 `DATABASE_URL` 的端口号要一致 |
| `BACKEND_PORT` | 不用改，前端代理会自动跟着（`vite.config.ts` 读同一个配置） |
| `FRONTEND_PORT` | 不用改 |

启动脚本会**先探测端口**：如果发现被别的程序占了，会直接告诉你是谁占了、怎么改，
而不是丢一句"启动失败"让你猜。

脚本的几个贴心设计：

- **已运行的部分自动跳过**，不会重复开窗口
- **等真正就绪才开浏览器**，不会出现白屏
- **停止时按 PID 精确识别**，绝不按进程名批量杀，不会误伤你机器上别的项目

### 手动启动（4 步）

> 需要自己控制每一步时用这个。每一步都给了完整命令，复制即可。

#### 0. 环境要求

| 依赖 | 版本 | 用途 |
|------|------|------|
| Docker Desktop | 任意较新版本 | 跑 PostgreSQL + Qdrant |
| Python | 3.11+（实测 3.12） | 后端 |
| Node.js | 18+ | 前端构建 |

#### 1. 配置密钥（只需一次）

```bash
cd backend
copy .env.example .env        # Windows
# 然后把 .env 里的两个 Key 填成你自己的：
#   EMBEDDING_API_KEY = 阿里云百炼 Key（向量模型，必填）
#   LLM_API_KEY       = DeepSeek Key（对话模型，必填）
# 申请地址见 .env.example 内注释
```

#### 2. 启动数据库（Docker）

```bash
docker compose up -d
```

会启动两个容器：`kbqa-postgres`（5432）与 `kbqa-qdrant`（6333/6334）。

#### 3. 启动后端

```bash
# 建议先建虚拟环境并装依赖：
python -m venv .venv
.venv/Scripts/pip install -r backend/requirements.txt

# 启动后端
# 端口与根目录 .env 的 BACKEND_PORT 保持一致（默认 8000）
.venv/Scripts/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

后端就绪后：
- API 文档（Swagger）：http://127.0.0.1:8000/docs
- 健康检查：http://127.0.0.1:8000/api/v1/health

> 若根目录 `.env` 里改了 `BACKEND_PORT`，上面两处地址的端口要同步替换。

#### 4. 启动前端

```bash
cd frontend
npm install
npm run dev
```

浏览器打开 **http://127.0.0.1:5173** 即可使用（端口受 `.env` 的 `FRONTEND_PORT` 控制）。

> 💡 如果你不想手动跑上面四步，直接双击根目录的 **[选择启动.bat](选择启动.bat)** 即可：
> 它会按「Docker → 数据库 → 后端 → 前端 → 健康检查」的顺序自动完成，
> 并等每一步真正就绪后才继续（不是简单地把窗口开起来）。
> 关闭时双击 **[停止.bat](停止.bat)** 一键全停。

## 🧪 自动化测试

```bash
cd backend
.venv\Scripts\python -m unittest discover -s tests -t . -v
```

共 **537 个用例**，覆盖四个层次：

| 层次 | 覆盖内容 |
|---|---|
| **单元测试** | 切块逻辑、向量检索去噪、闲聊识别、开放意图识别、内容过滤、额度计算、任务队列、密码策略 |
| **HTTP 集成测试** | 真实 ASGI 请求走完整链路：鉴权（401/403）、跨组织越权、SSE 流式事件、Cookie 安全属性 |
| **并发测试** | 额度原子扣减（需要真实 PostgreSQL，CI 里会自动起一个） |
| **回归测试** | 上述每个修复过的 bug 都有一条用例锁死，防止改回去 |

> 其中 3 个用例在 SQLite 下会跳过（连接池参数、真并发额度），CI 里配了 PostgreSQL 所以会真正执行。

前端另有 **9 个用例**（Node 内置测试运行器，无需额外依赖），覆盖 401 分类逻辑：

```bash
cd frontend
npm test
```

CI 配置见 [.github/workflows/ci.yml](.github/workflows/ci.yml)：
后端测试 + 前端单元测试 + 前端构建 + 依赖漏洞审计 + 密钥扫描。

## 📝 使用流程（第一次体验）

1. 打开 http://127.0.0.1:5173 → **注册账号**
2. 进入知识库 → **新建知识库**（如"商品资料库"）
3. 在知识库内**上传文档**：可直接使用 `样例资料/` 目录里的文件
   （`商品总览.md`、`星翼智能手表Watch2手册.pdf`、`星翼蓝牙耳机Pro说明书.docx`、`星耀空气净化器A8.md`、`星翼数码商品价格表.xlsx` 等）
4. 等文档状态变为"已入库" → 进入**聊天**，选择该知识库
5. 开始提问，例如：
   - "Watch2 的电池续航怎么样？"（具体问答）
   - "介绍一下本商品的型号和价格"（开放意图 → 自动列出商品清单）
   - "你好"（闲聊 → 不查库，正常打招呼）
